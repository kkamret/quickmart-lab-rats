## 스펙에 값이 없어 가상으로 둔 것
- 전체 배정 코호트(install_all) 일 40만 명, 후기 수신자 일 33만, 진입률 0.62
- 전체 배정 코호트 중 후기 화면 진입 비율 `ALL_ASSIGNED_ENTRY` = 204,600 / 6,000,000 ≈ 3.4%(숨김 상수, 가상). install_all + all_assigned 의 관측 효과가 약 0.15%p 로 희석되는 근거
- SDK 구성(안드로이드 구/신, iOS) 비율, 신규 사용자 비율 9%
- 앱 삭제율·신고율 기저값, 재시도율 기저 0.18, 시작률/제출률 기저
- 사용자 의견 6개(content.ts), 검색 사용자 일 40만, 신규 게시글 일 6만, 동네 6,500개와 ICC
- 신규 사용자 중 설치 후 24시간 이내 비중 0.4(`NEW_FIRST_DAY_SHARE`). 신규 설치 버그로 이 코호트의 약 90%가 대조군에 있게 된다(트리거 모집단의 약 3%를 대조군으로 강제)

## 스펙과 다르게 한 결정 (PR에도 기재)
1. **UNDERPOWERED 규칙**: 시나리오 #4는 표본이 매우 커서 통계적 검정력이 높게 나온다(관측 약 0.15%p, p ≈ 1e-51 로 유의). 참 효과가 MDE의 25% 미만이면 달성 검정력을 0.25로 제한해, 설계가 의도한 질문에 답하지 못한 경우를 잡는다. 그래서 시나리오 #4 는 mde_pp = 2 를 명시하고, mde_pp ≤ 0.6 이면 이 규칙이 꺼져 UNDERPOWERED 가 사라진다.
2. **p2는 p1 설계를 이어받음**: s5에서 거래후기 설계 칸(배정 시점·분석 모집단·지표 등)은 선택 입력이고, 비어 있으면 안내와 함께 거부한다.
3. **A/A 실행**은 설계에서 `run_aa_first`(p1) / `rerun_aa`(p2)를 고르지 않았으면 거부한다.
4. **진단 패널 게이트**: 플랫폼 진단(설치 코호트·양쪽 그룹 중복)은 A/A에서는 바로 열리고, 본 실험에서는 UI의 "조사하기" 버튼 뒤에 둔다. 데이터는 API 응답에 포함된다(숨김 정보는 아님).
5. **`meta` 패널 추가**: UI가 A/A 여부와 플랫폼을 알 수 있도록 `{aa, platform|unit}`을 내린다.
6. 이 사례는 모집단이 크고 셀 단위(유형 × SDK)로 이항 표본을 만드는 방식이다. 토스처럼 사용자 모멘트 닫힌 형태가 아니다.
7. **분석 모집단 검증은 실행 시점에만** 한다(설계 폼은 아무 조합이나 제출 가능, 배정보다 넓은 모집단이면 시뮬레이션이 거부). `all_assigned` 는 "배정된 전원"이라 언제나 허용된다. install_all 배정 + 화면 진입자 분석은 review_screen_open 배정과 같은 결과다(정당한 트리거 분석).
8. **CONTAMINATION 은 배정 키만으로 정한다**(그룹 이동 비중 3% 이상: 인스턴스 ID 14%, 기기 ID 6%). 스펙의 "인스턴스 단위로 분석하면 중복 집계" 는 별도 분석 선택지로 모형화하지 않았다. 분석은 늘 사용자 ID 조인 + 첫 배정 귀속이다.
9. **중간 확인 규칙**: 하루 표본이 매우 커서 peek_stop·sequential 모두 A/A 가 아닌 설계는 대부분 1일차에 멈춘다(install_all + all_assigned 의 sequential 만 3일차). PEEKED 는 peek_stop 에만 붙는다. A/A 실행은 설계의 규칙과 무관하게 늘 fixed 다.
10. **계획 표본(planned)**: p1·p2 는 하루 유입이 커서 계획 기간이 늘 1일로 나와 의미가 없다. p3 에서만 의미 있게 읽는다.
11. **started 지표 효과**: 화면 진입자·server_db 기준 약 +7.5%p, client_events 면 중복 이벤트까지 얹혀 약 +9%p.
12. **판매완료율(사용자 배정)**: 관측 +0.7% 도 표본이 커서 7일부터 유의하다(검정력 7일 0.59, 14일 0.87, 21일 0.97).

## 한계
- 효과 값은 시나리오 범위에 맞춘 것이지 원문 실측이 아니다.
- 동네 클러스터 상관은 ICC·DEFF 모형이며, 개별 동네를 생성하지는 않는다. 스펙의 "동네 크기 로그정규(평균 활성 사용자 3,000명)"는 구현하지 않았고, 쓰이지 않던 상수 `NEIGHBORHOOD_SIGMA` 는 지웠다. 동네 패널의 동네당 사용자 수는 (일 검색 사용자 40만 × 기간 ÷ 2) ÷ 동네 3,250개라 28일이면 약 1,723명이다(스펙의 3,000명과 다름).
