## 3. 실험 단위 결정

실제 실험으로 들어가게되면 가설과 지표를 잘 정하는 것만으로는 부족합니다. 잘못된 단위로 사용자를 나누거나 분석하면 Treatment의 효과를 제대로 추정할 수 없습니다. 따라서 A/B 테스트에서는 ‘무엇을 A와 B로 나눌 것인가’를 먼저 명확하게 정의해야 합니다.

한 문장으로 말하면 <strong>인과효과를 제대로 분리하기 위함</strong>인거죠

### 3.1 Experimental Unit(실험 단위) / Randomization Unit (랜덤 배정 단위)

> “무엇 하나를 독립적인 실험 관측 대상으로 보고 A/B를 나눌 것인가?”

<strong>Experimental Unit</strong>은 실험에서 하나의 Treatment를 독립적으로 배정받는 기본 단위입니다.

<strong>Randomization Unit</strong>는 실험에서 Control과 Treatment 중 하나에 무작위로 배정되는 기본 단위를 말합니다. 즉, 랜덤 배정을 수행하는 단위인거죠. 온라인 A/B 테스트에서는 일반적으로 Experimental Unit과 동일하게 사용됩니다.

예를 들어 지금 공부하고 있는 A/B 테스트에서는 User, Session, Page View, Device, Cookie 등이 Randomization Unit이 될 수 있습니다.

### 3.2 User-level Randomization (사용자 수준 무작위 배정)

가장 직관적인 방법으로는 사용자 한 명을 실험 단위로 보고 무작위 배정을 하는 것입니다.

각 사용자는 무작위로 대조군 또는 실험군에 배정되며, 사용 기기, 세션 또는 활동과 관계없이 실험이 끝날 때까지 같은 그룹을 유지합니다.

즉 사용자 수준의 무작위 배정의 핵심은 <strong>한 사용자에게 실험 기간 동안 일관된 Variant를 제공한다</strong>는 것 입니다.

서비스 상황(로그인 서비스 / 비로그인 서비스 등)에 따라 사용자를 식별하는 기준은 여러가지가 있을 수 있습니다.

#### 3.2.1 같은 사용자를 같은 그룹에 유지해야하는 이유 - Sticky Assignment

그렇다면 왜 User 단위로 나누는 것일까요? 가장 큰 이유는 사용자 경험(UX)의 일관성 입니다.

예를 들어 결제 화면을 실험한다고 했을 때 사용자가 첫 번째 방문에서는 A화면을 보고, 다음 방문에서는 B를 본다면 사용자 경험이 섞여버리게 되겠죠. 이렇게 되면 이전 경험이 이후 행동에도 영향을 줄 수 있는 실험에서는  문제가 커지게 됩니다.

그래서 User-level에서는 동일 사용자 → 동일 Variant라는 일관성을 유지합니다. 이를 흔히 <strong>Sticky Assignment</strong>라고 합니다.

#### 3.2.2 User-level의 장점

1. **통계적 독립성 가정을 적용하기 비교적 용이하다**

	사용자를 무작위 배정 단위로 설정하면 한 사용자의 여러 방문·클릭·구매가 하나의 실험 단위 안에 묶입니다. 따라서 같은 사용자가 만든 여러 행동을 서로 독립적인 표본처럼 잘못 취급하는 문제를 줄일 수 있습니다.

	\*다만 사용자 간 추천·공유처럼 서로 영향을 주는 구조가 있다면 사용자 수준으로 배정하더라도 완전한 독립성이 보장되는 것은 아닙니다.

2. **일관된 사용자 경험을 제공한다**

	한 번 Control 또는 Treatment에 배정된 사용자가 실험 기간 동안 계속 같은 Variant를 경험하도록 유지할 수 있습니다. 따라서 방문할 때마다 UI, 가격, 추천 방식 등이 바뀌어 발생하는 혼란이나 이전 Treatment의 영향이 다음 경험에 섞이는 문제를 줄일 수 있습니다.

3. **누적 지표 측정에 적합하다**

	리텐션, 재구매율, 사용자당 매출, 누적 사용 횟수처럼 여러 방문에 걸쳐 형성되는 지표는 사용자를 계속 같은 Variant에 유지할 때 Treatment의 누적 효과를 해석하기 쉽습니다.

#### 3.2.3 User-level의 단점

1. **개인정보나 프라이버시 부담이 있다**

	사용자 단위로 배정하고 추적하려면 user_id, device_id, 쿠키 같은 식별자를 로그에 남겨야합니다. 이러한 식별자는 개인에게 연결되기 때문에 보안에 신경써야 합니다.

2. **사용자를 지속적으로 식별해야 한다**

	같은 사용자를 같은 그룹에 유지하려면 실험 기간 내내 같은 식별자로 알아볼 수 있어야 합니다.

	- 쿠키를 삭제하거나 브라우저/기기를 바꾸면 같은 사람이 새 사용자로 인식되어 다른 그룹에 배정될 수 있습니다.

	- 로그인 전 후로 식별자가 달라지면 같은 사람이 두 그룹이 걸칠 수 있습니다.

	어떤 식별자를 고르냐에 따라 이 한계를 어디까지 줄일 수 있는지 결정할 수 있겠죠

3. **표본이 쌓이는 속도가 느릴 수 있다**

	User-level의 단위 수는 고유 사용자 수 입니다. 한 사용자가 하루에 여러 번 방문해도 단위는 1개 입니다.

	그래서 필요한 표본 크기에 도달하기까지 시간이 더 걸릴 수 있고, 방문 빈도가 낮은 서비스에서는 이런 점이 크게 다가오겠죠?

정리하면, 사용자 수준의 배정은 제품 기능 테스트, 가격 실험 같이 일관되고 장기적인 사용자 경험이 중요한 경우에 적합하며, 온라인 A/B 테스트에서 가장 일반적으로 사용되는 방식입니다.

### 3.3 Session-level Randomization

Session-level Randomization은 <strong>한 번의 방문 세션(Session)을 기준으로 Control과 Treatment를 배정</strong>하는 방식입니다.

예를 들어 사용자가 여러 번 방문하면, 세션이 바뀔 때마다 다른 실험 조건에 배정되는 것이죠

```text
User A
├─ Session 1 → Control
├─ Session 2 → Treatment
└─ Session 3 → Control

```

#### 3.3.1 Session의 정의

Session은 보통 사용자가 서비스에 들어와 일정 시간 동안 연속적으로 활동한 하나의 방문 묶음을 의미합니다.

그래서 한 사용자는 여러 세션에 걸쳐 대조군과 실험군 모두를 경험할 수 있습니다.

예를 들어 `앱 접속 → 숙소 검색 → 상세페이지 확인 → 예약 → 앱 종료` 까지의 Session으로 정의할 수 있습니다.

그래서 Session-level에서는 보통 단위가 Session, Randomization Key가 session_id가 됩니다.

#### 3.3.2 Session-level은 언제 사용하는가

Session-level은 그 방문 한 번으로 끝나는 변화를 테스트할 때만 씁니다. 오늘 본 화면이 다음 방문의 행동에 영향을 주지 않는다고 말할 수 있어야 합니다.

다만 이런 조건을 만족하는 경우는 드물겠죠.. 알림, 팝업, 배너 광고 등은 한 번 보여주고 끝나는 변화처럼 보여도 사용자의 경험은 다음 방문으로 이어질 수 있으니까요.

따라서 이런 종류의 실험은 Session-level을 써도 된다/안된다가 아니라 “이 변화를 본 사용자가 다음 방문에서 행동이 달라질 가능성이 있는가?(=이월 효과가 있는가?)”라는 질문에 가능성이 낮다면 Session-level을 고려하고, 높다면 User-level을 기본으로 선택합니다.

#### 3.3.3 Session-level의 장점

1. **단위 수가 빨리 늘어난다**

	같은 트래픽에서 단위 수(세션)가 사용자 수보다 훨씬 빨리 늘어납니다. 한 사용자가 하루에 세 번 방문하면 User-level에서는 단위가 1개, Session-level에서는 3개입니다. 그래서 필요한 표본에 더 빨리 도달할 수 있습니다. 그렇기 때문에 자주 방문하는 사용자의 세션이 더 많이 반영 됩니다. 결과는 ‘평균적인 사용자’가 아니라 ‘평균적인 세션’에 대한 결론이 됩니다.

2. **영구적인 사용자 ID에 덜 의존한다**

	세션 간 사용자를 안정적으로 식별하기 어려운 서비스에서도 실험할 수 있습니다. 쉽게 말해 같은 사람이 오늘 오고 내일 또 와도, 서비스 입장에서는 ‘처음 보는 사람’처럼 보이는 경우입니다.

	예를 들어, 아래와 같은 상황을 예시로 생각할 수 있겠죠.

<table header-row="true">
<tr>
<td>상황</td>
<td>왜 식별이 어려운가</td>
</tr>
<tr>
<td>로그인이 없는 웹사이트 (뉴스, 정보성 페이지 등)</td>

</tr>

</table>

#### 3.3.4 Session-level의 주의점

1. **이월 효과로 결과가 오염될 가능성이 있다**

	항상 그런 것은 아니지만, 한 사용자가 A와 B를 번갈아 경험하면, 앞선 세션에서 본 B의 영향이 뒤 세션의 A 그룹 결과에 섞입니다.

	예를 들어 두 번째 세션에서 B를 본 사용자가 세 번째 세션에 A를 보고 구매했다면, 그 구매는 A의 성과로 집계됩니다. 이렇게 두 그룹이 서로의 경험을 공유하면 그룹 간 차이가 작게 측정될 수 있습니다.

	즉, B만의 효과를 깨끗하게 정의하기가 어려워집니다.

2. **사용자 경험 자체가 흔들릴 수 있다**

	사용자가 변화를 명확하게 인지하는 기능은 세션마다 A/B가 바뀌면 부자연스럽게 느껴질 수 있기 때문에 세션마다 Variant가 바뀌어도 괜찮은 기능인지 확인해야 합니다.

	따라서 **같은 사용자가 다음 방문에서 다른 버전을 봐도 실험 자체를 방해하지 않는지** 확인해야합니다.

### 3.4 Page-level / Request-level Randomization

위에서 말한 User나 Session보다 더 세밀한 단위로 랜덤화하는 방식입니다.

<strong>Page-level Randomization</strong>은 페이지 조회(Page View) 하나하나를 기준으로 Control과 Treatment를 배정하는 방식이고, <strong>Request-level Randomization</strong>은 서버/API 요청 하나하나를 기준으로 배정하는 방식입니다.

한 페이지에서는 여러 개의 API Request가 발생할 수도 있기 때문에 둘을 구분해서 보는 것이 좋습니다.

#### 3.4.1 Page/Request-level은 언제 사용하는가

“사용자 경험”이 아니라 요청이나 페이지 자체의 성능을 보는 실험에서 사용합니다. 이런 실험에서는 사용자 단위 지표를 못 보는 것이 손해가 아니고, 오히려 비교가 또렷해지는 이점을 얻을 수 있습니다.

1. **알고 싶은 것이 요청 하나하나의 성능일 때**

	서버가 응답하는 방식 A와 B 중 어느 쪽이 더 빠른지 비교한다고 해봅시다. 이때 궁금한 것은 “요청 한 건을 처리하는 데 어느쪽이 더 빠른가”입니다. 그러면 사람이 아니라 요청 한 건 한 건을 나눠서 비교해야 합니다.

2. **차이를 더 또렷하게 잡아내고 싶을 때**

	같은 사용자가 A화면과 B화면 둘 다 경험하면, 그 사용자의 원래 성향이 양쪽에 똑같이 반영됩니다. 그렇기 때문에 A와 B의 차이가 더 선명하게 남을 수 있습니다.

따라서 반대로 리텐션이나 구매 같은 장기 사용자 지표를 핵심적으로 보려는 실험에는 쓰지 않습니다.

#### 3.4.2 Page-level / Request-level의 주의점

1. **효과가 정말 그 페이지·요청 안에서 끝나는지 확인한다.**

	Page-level은 같은 사용자가 Variant를 번갈아 경험하는 것을 전제로 하는 방식입니다.

	그래서 앞에 본 화면이 뒤에 행동에 영향을 남기지 않는다 같은 전제가 필요합니다.

2. **판단 지표를 배정 단위와 같은 수준에 둔다.**

	지표는 배정 단위와 같거나 더 작은 단위여야 합니다. 같은 사용자가 두 Variant를 모두 경험하므로, 사용자 단위로 쌓이는 지표는 어느쪽의 효과인지 가를 수 없습니다. 그래서  페이지 로딩 시간이나 요청 응답시간처럼 같은 수준의 지표로 판단합니다.

3. **같은 사용자의 관측은 서로 닮아있다고 보고 분석한다.**

	같은 사용자에게서 나온 관측은 서로 닮는 경향이 있습니다. 그렇기 때문에 단위 수만큼 독립적인 정보가 있는 것은 아닙니다. 이를 무시하고 모두 독립으로 보고 계산하면 불확실성이 실제보다 작게 계산될 수 있습니다.

### 3.5 한 사용자가 여러 번 노출되는 경우

앞에서는 실험 단위를 어떻게 나눌지를 봤습니다. 온라인 서비스에서는 한 사용자가 실험 기간 동안 Treatment를 한 번만 경험하는 경우보다 여러 번 반복해서 경험하는 경우가 많습니다. 그럼 반복 노출이 생기면 실험 효과를 어떻게 해석해야할까요?

#### 3.5.1 같은 Variant에 반복해서 보면 효과가 달라질 수 있다

User-level에서의 반복 노출은 문제가 아니라 설계의 의도입니다. 그런데 이때, Treatment의 효과가 처음부터 끝까지 일정하다는 보장은 없습니다. 즉, 초기 효과와 장기 효과가 다르다는것 인데요.

예를 들어,

- 새 UI가 낯설어서 초반에는 지표가 떨어졌다가, 익숙해지면서 올라갈 수 있습니다.

- 새롭다는 이유로 초반에만 반응이 크다가 점점 줄어들수도 있습니다.

이렇게 한 사용자가 Treatment를 여러 번 경험할 때 결과를 어떻게 읽어야할까요?

1. **전체 평균 하나만 보지 말고, 실험 시작 후 며칠째인지 기준으로 효과의 추이를 함께 봐야합니다.**

	예) 1\~3일차, 4\~7일차, 8\~14일차

2. **노출 횟수별로 쪼개서 보지 않습니다.**

	노출 횟수는 실험이 시작된 뒤에 사용자의 행동으로 정해지는 값입니다. <strong>활동적인 사용자일수록 많이 노출</strong>되기 때문에 ‘5회 사용자 vs 1회 사용자’를 비교하면 **사용자의 성향 차이를 보게 됩니다**. 하지만 시간 경과는 두 그룹에 똑같이 적용되기 때문에 랜덤 비교가 유지됩니다.

3. **Assigment(어느 그룹에 배정됐는지)와 Exposure(실제로 경험했는지)를 구분해서 기록합니다.**

	Treatment에 배정된 사용자가 해당 화면에 한번도 방문하지 않을 수도 있기 때문입니다. 실제로 영향받을 수 있는 사용자만 분석에 포함하면 노이즈가 줄어 효과가 더 정확하게 추정됩니다.

### 3.6 Randomization Unit과 Analysis Unit

Randomization Unit은 <strong>Control과 Treatment를 배정하는 단위</strong>이고, Analysis Unit은 <strong>결과를 비교하는 관측 단위</strong>입니다. 배정한 단위와 결과를 계산하는 단위가 다를 때는 무엇이 달라질까요?

#### 3.6.1 배정 단위와 분석 단위의 조합

사용자 > 세션 > 페이지·이벤트 순으로 단위가 작아진다고 할 때, 배정 단위보다 큰 단위로는 지표를 정의할 수 없습니다.

#### 3.6.2 배정 단위가 분석 단위보다 클 때 생기는 문제

사용자 1,000명을 Control과 Treatment에 배정했는데 실험 기간 동안 총 10,000개의 세션이 발생했다고 해봅시다.

```text
1,000 Users
     ↓
10,000 Sessions
```

세션이 10,000개라고 해서 <strong>10,000개의 독립적인 정보가 생긴 것은 아닙니다.</strong>

예를 들어 User A가 만든 세션이 10개라면:

```text
User A
├─ Session 1
├─ Session 2
├─ Session 3
...
└─ Session 10
```

이 10개 세션에는 User A의 구매 성향, 방문 습관 같은 공통 특성이 반영됩니다. 따라서 서로 완전히 독립적인 사용자 10명이 만든 세션처럼 취급할 수 없습니다.

그런데 세션 10,000개를 모두 독립적인 표본이라고 가정해 일반적인 공식을 적용하면,

> 표본이 실제보다 많은 것처럼 보임
>
> → 불확실성을 작게 추정
>
> → 신뢰구간이 지나치게 좁아짐
>
> → 실제 효과가 없는데도 유의하다고 판단할 가능성이 높아짐

이라는 문제가 생길 수 있습니다.

#### 3.6.3 실제로 얼마나 문제가 될 수 있을까?

Microsoft 연구자들의 시뮬레이션에서는 <strong>사용자 단위로 랜덤 배정한 뒤 페이지 수준 데이터를 단순 공식으로 분석했을 때</strong>, 실제 Treatment 효과가 없는 설정에서도 명목상 95% 신뢰구간이 참값을 포함하는 비율이 크게 떨어지는 경우가 나타났습니다.

일부 시뮬레이션에서는 그 비율이 약 <strong>47%, 74%</strong> 수준까지 낮아졌습니다.

원래 95% 신뢰구간이라면 같은 실험을 반복했을 때 약 95% 정도는 참값을 포함해야 하는데, 반복 관측 구조를 무시하면 이 성질이 크게 무너질 수 있다는 의미입니다.

다만 이 수치는 <strong>특정 시뮬레이션 조건에서 나온 결과</strong>이므로, “실제 서비스에서도 항상 47%가 나온다.”는 의미는 아닙니다.

여기서 기억할 것은 숫자 자체보다, “<strong>Randomization Unit과 Analysis Unit을 무시하면 단순한 오차 수준이 아니라 통계적 추론 자체가 크게 왜곡될 수 있다</strong>”는 점입니다.

#### 3.6.4 해결 방법 ① 배정 단위로 다시 집계하기

가장 직관적인 방법은 <strong>Randomization Unit에 맞춰 지표를 다시 집계하는 것</strong>입니다.

User-level로 배정했다면 사용자별 지표를 만든 뒤 Control 사용자와 Treatment 사용자를 비교하는 방식입니다.

예를 들어:

```text
User A → 10개 세션 중 1개 전환 → 10%
User B → 1개 세션 중 1개 전환 → 100%
```

이때 사용자별 전환율을 계산한 뒤 평균을 내면 $`\frac{10\%+100\%}{2}=55\%`$가 됩니다.

그런데 전체 세션을 합쳐서 계산하면 $`\frac{2}{11}\approx18\%`$입니다.

같은 데이터인데 결과가 크게 다릅니다. 왜냐하면 두 지표가 <strong>서로 다른 질문</strong>에 답하기 때문입니다.

- `2 / 11 ≈ 18%` → 전체 세션 중 얼마나 전환되었는가?
- `(10% + 100%) / 2 = 55%` → 평균적인 사용자의 세션 전환율은 얼마인가?

따라서 단순히 “User-level로 집계하면 더 정확하다”고 말하기보다, <strong>분석 단위를 바꾸면 지표의 의미와 사용자별 가중치도 달라질 수 있다는 점</strong>을 확인해야 합니다.

#### 3.6.5 해결 방법 ② 지표는 유지하고 불확실성 계산을 보정하기

세션 단위 CVR처럼 <strong>지표 정의 자체를 유지해야 하는 경우</strong>도 있습니다.

예를 들어 서비스 전체 관점에서 $`\frac{\text{전환 세션 수}}{\text{전체 세션 수}}`$를 그대로 보고 싶다면, 이를 사용자별 평균으로 바꾸는 것은 원래 지표와 다른 질문이 됩니다.

이 경우에는 지표 정의는 유지하되, <strong>같은 사용자에게서 발생한 여러 세션이 서로 묶여 있다는 사실을 반영해 표준오차와 신뢰구간을 계산</strong>해야 합니다.

<strong>Randomization Unit과 Analysis Unit이 다르면 일반적인 독립 표본 공식이 그대로 적용되지 않을 수 있으므로, 그 구조에 맞는 분산·불확실성 추정이 필요</strong>합니다.

### 3.7 어떤 단위를 선택해야 하는가?

실험에서 우리가 나누고 싶은 대상은 결국 ‘사람’입니다. 하지만 서비스가 알아볼 수 있는 것은 계정, 기기, 쿠키 같은 식별자 뿐입니다. 쿠키를 쓰게 되면 사람이 브라우저나 기기를 바꾸거나 쿠기를 지우면 다른 사용자로 보이게 되죠. **그래서 어떤 단위를 고르든 사람의 근사치(=불완전한 프록시)를 쓰는 것이고**, 각 단위는 장단점이 있을 뿐, 완벽한 정답은 아닙니다.

그래서 실험의 목적과 환경에 맞게 적절한 방법을 선택해야합니다.

Microsoft 연구자들은 대부분의 실험이 사용자를 랜덤화 단위로 쓴다고 설명합니다. 이유는 두 가지입니다.

1. 많은 변경에서 사용자에게 일관된 경험을 줘야 하고,

2. 대부분의 지표가 사용자 단위(사용자당 세션 수 등)로 계산되기 때문입니다.

그래서 <strong>User-level에서 시작하고, 다른 단위를 쓸 때는 이유를 설명할 수 있어야 한다를 기본 원칙으로</strong> 삼으면 됩니다.
