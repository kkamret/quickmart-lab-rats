# 배민 실습: 모든 선택지에 "왜 이 선택지?" 한 줄 달기 (설계)

- 작성일: 2026-10-09 (사용자 결정 반영: 같은 날 개정)
- 범위: 배민 사례(`lib/cases/baemin`)의 진단 → P1 설계·실행·결과·결정 → P2 → P3 → P4 → s7 함정 연구소 → s8 직소 공유. 앱 코드는 이 문서에서 바꾸지 않아요.
- 브랜치: `feat/baemin-choice-rationale` (`feat/baemin-theory-logic` 위). PR #20과 별도 PR로 내요.
- 함께 읽을 문서: `docs/cases/baemin.md`(진실의 원천), `docs/superpowers/specs/2026-10-09-baemin-theory-logic-design.md`(판정 로직), `docs/theory-coverage.md`(패러프레이즈 은행), `lib/theory.ts`(THEORY, FIELD_THEORY, STEP_THEORY).

## 0. 사용자 결정 기록

1. **근거가 없으면 줄을 쓰지 않는다.** 덱·위키에 근거가 없는 이론 문장은 만들지 않아요. `analysis_mode = pooled`는 줄 없이 둬요. 공통 화면(s7·s8)의 근거 없는 기존 문구('승률보다 학습률', SRM 'p < 0.001')는 2단계에서 덱이 말하는 범위로 맞춰 지워요(5장). 진단 보기(네·아니요·잘 모르겠어요)는 줄 없이 둬요.
2. **사례 고유 지표·사실은 덱 근거 없이도 된다.** `cs_rate`, `min_reach`는 사례 문서를 근거로 "무엇을 재는지, 이 사례가 왜 재는지"만 말해요. 사례 문서 §0의 설계 사실(P3 노출 조건, P4 B·C 정의 등)과 지표 문장의 영역 이름(제품 안정성, 장기 가치)은 승인됐어요.
3. **근거 표시는 챕터만.** 줄마다 `Ch1`~`Ch5` 또는 `사례`만 저장하고 보여 줘요. 슬라이드 제목·위키 편·절·원문 조각은 표와 코드에 두지 않아요. 테스트 전용 출처 파일과 원문 일치 테스트도 두지 않아요. "덱·위키 내용만 쓴다"는 **작성 규칙**으로 남고, 검토자가 덱과 대조해 확인해요.
4. **기존 맥락 문구는 그대로 둔다.** `scope.os=all` desc "iOS 구버전 사용자가 포함돼요", `coupon_ops` low·high desc, `rationale` help "(교란)"은 고치지 않아요. 학생에게 그 정도 맥락은 필요하고, 모든 걸 숨겼다가 "갑자기 버그"를 내미는 건 좋지 않다는 판단이에요. 스포일러 테스트는 이 문구들을 명시적 허용 목록으로 두고, **새 why 줄**에는 계속 엄격하게 적용해요.

## 1. 목표·비목표·원칙

### 1.1 목표

- 배민 실습 흐름에서 학생에게 보이는 **모든 선택**(select·multiselect·boolean 보기, number·text 입력란의 목적, 결정 보기, 진단 입력란, 실행 버튼)에 "왜 이 선택지가 있는지"를 한 줄로 보여 줘요. 학생이 설계·선택·실행하면서 이론을 떠올리게 하는 게 목적이에요.
- Phase(진단, P1 설계, P1 실행, P1 결과·결정, P2, P3, P4, s7, s8)마다 "왜 여기 왔고, 앞 결과가 무엇으로 이어지는지"를 2~3줄 다리 문장으로 보여 줘서, 모든 선택이 하나의 큰 흐름 안에서 이어지게 해요.
- 줄마다 근거 챕터(`Ch1`~`Ch5`) 또는 `사례`를 붙여요.

### 1.2 비목표

- 정답·오답을 알려 주지 않아요. 맞다/틀리다는 지금처럼 정답 공개(판정 근거 `judge` reason, 플래그 `why`)에서만 보여요.
- 시뮬레이터, 판정 로직, 루브릭은 바꾸지 않아요.
- 토스·당근·넷플릭스는 이번 범위가 아니에요. UI 변경은 공통 컴포넌트에 들어가지만, why 데이터가 없는 사례는 지금과 똑같이 보여요.
- 덱·위키를 고치지 않아요.

### 1.3 원칙

1. **작성 규칙: 덱·위키 내용만.** 이론 문장은 덱 또는 위키 문장의 가까운 패러프레이즈로만 써요. 근거가 없으면 줄을 쓰지 않아요. 검토자가 덱과 대조해 확인해요(코드에는 원문 조각을 두지 않아요).
2. **사례 사실은 사례 문서에서.** 유입·세그먼트 비중·대조군 기준값·협의 MDE·기능 정의는 `docs/cases/baemin.md`(§0 설계 부분, §1, §3-1b)에서 가져와요. §2(숨긴 효과), §3-2(반영 규칙), §3-3(플래그)의 숫자와 규칙, §0의 **결과** 부분(예: "충족자가 적었음")은 쓰지 않아요.
3. **스포일러 금지(새 줄).** 새 why 줄과 다리 문장은 함정 이름(SRM, 심슨, 생존 편향, 신규성 효과, Peeking 등), 플래그 코드·라벨(`FLAG_LABELS`), 숨긴 효과 숫자, revealOnly 개념 이름, "틀렸다/맞다" 힌트를 담지 않아요. "이 보기가 왜 있는지, 어떤 상황에서 쓰는지"만 중립적으로 말해요. 예: `peek_stop`이 위양성을 늘린다고 말하지 않고, 세션·페이지뷰가 틀렸다고 말하지 않아요. 덱 문장에 함정 결과가 함께 있으면 "언제 쓰나" 부분만 가져와요.
4. **기존 맥락 문구는 유지(0장 4).** 테스트에서 명시적 허용 목록으로 다뤄요.
5. **한 선택지에 한 줄.** 보기마다 한 줄(길어도 두 문장), 입력란 목적은 입력란 줄 한 개.
6. **근거 표시는 챕터만.** 앱에는 줄 옆에 작은 챕터 배지(`Ch3`, 기존 `TheoryBadge`와 같은 모양) 또는 `사례` 배지만 보여요. 슬라이드 번호·제목, 위키 편·링크는 앱에 없어요. 다리 문장의 개념 라벨은 기존처럼 `theoryLabel`(revealOnly 개념이면 `theoryChapterOnly`)을 써요.
7. **기존 테스트를 지킨다.** `lib/__tests__/theory.test.ts`의 "THEORY note 문장을 폼 문구에 그대로 넣지 않는다", "revealOnly 개념은 s7 밖 스텝 이론 줄에 넣지 않는다"를 새 문구에도 적용해요(6장).
8. **앱 동작 안내.** "제출한 설계대로 돌아가요"처럼 앱 동작을 말하는 부분은 이론 주장이 아니에요. 그런 부분이 있는 줄도 이론 내용의 챕터로 표시해요.

## 2. 흐름 지도

### 2.1 큰 흐름

덱 Ch1의 7단계(목표와 지표 → 가설 → 대조군·실험군 → 무작위 배정 → 실행과 데이터 수집 → 분석과 비교 → 결정과 반복)를 배민 네 번의 실험에 겹치면 아래처럼 이어져요.

```text
s1 진단(관찰 데이터, 문제 좁히기)
  └─ s2 P1 설계(가설 → 범위 → 단위 → 지표 → α·검정력 → 기간·투입 → 램프업·분석·중간 확인·집계)
       └─ s3 P1 실행(A/A로 시스템 점검 → 본 실험)
            └─ s4 P1 결과 읽기 → 결정(배포·접기·재실험)
                 └─ s5 P2 확대(내적 → 외적 타당성) → 결과 → 결정(배포 + 다음 가설)
                      └─ s5 P3 혜택 넛지(Secondary·Driver에서 다음 가설) → 결과 → 결정
                           └─ s6 P4 부족 금액 추천(A/B/n) → 결과 → 결정
                                └─ s7 함정 연구소(앞에서 스친 함정을 이름과 함께)
                                     └─ s8 직소 공유(효과 크기 × 비용 × 리스크로 말하기, 배운 점 남기기)
```

### 2.2 Phase별 다리 문장

`근거` 칸은 챕터(`Ch1`~`Ch5`) 또는 `사례`예요. s5에는 P2·P3 Phase가 **한 화면에 함께** 보이므로(`StepView`가 스텝의 Phase를 모두 그림), P3 다리 문장이 P2 결정 전에 보일 수 있어요. 그래서 P2·P3 결과는 어떤 다리 문장에도 넣지 않았어요.

## 3. 선택지 전수 목록

### 3.0 범례와 집계

- 상태: `초안`(근거 있음, 스포일러 OK) / `초안·주의`(근거 있음, 스포일러 검토 필요) / `줄 없음`(사용자 결정에 따라 문장을 두지 않음: 근거 없음 또는 보기 문장이 곧 답).
- 근거 칸: 이론 문장이 기댄 덱 챕터(`Ch1`~`Ch5`) 또는 `사례`. 사례 수치를 함께 쓰는 이론 줄은 챕터를 적고 "(+사례 수치)"를 덧붙였어요. 앱에는 챕터 또는 `사례` 배지 하나만 보여요.
- 현재 문구 칸은 코드 그대로예요(`formMeta.ts`, `decisions.ts`, `StepView.tsx`, `TrapLab.tsx`, `ShareStep.tsx`). `—`는 문구가 없다는 뜻이에요.
- 제안 한 줄은 앱에 보일 문장이에요. 덱·위키를 가리키는 말은 쓰지 않아요.

| 구역 | 입력란 | 보기(인스턴스) | 합계 | 초안 | 초안·주의 | 줄 없음 |

| 진단 | 2 | 3 | 5 | 1 | 1 | 3 |

- 지표 보기는 같은 11개가 Primary·Secondary·Guardrail 세 칸에 나와요. 문장은 지표마다 하나(11줄)를 세 칸에 같이 쓰고, 칸의 역할은 입력란 줄이 말해요. **고유 문장 기준**으로는 98개(= 120 − 22), 그중 문장 있음 94개, 줄 없음 4개(`pooled` 1, 진단 보기 3)예요.
- 열린 GAP은 없어요. 남은 일은 2단계 항목뿐이에요(5장).
- 공통 설계 필드는 P1·P2·P3·P4 폼에 반복해서 나와요. 문장은 한 벌만 두고, Phase별로 바꿔야 할 때만 Phase 덮어쓰기를 써요(4.2). 이번 초안에서 덮어쓰기가 필요한 줄은 없어요.
- 다리 문장(2.2) 16개 Phase/스텝은 위 집계와 따로 세요.

## 4. 데이터·UI 설계

### 4.1 타입 추가 (`lib/cases/types.ts`)

모두 선택 필드라 다른 사례는 바꾸지 않아도 컴파일되고 화면도 그대로예요.

```ts
import type { TheoryChapter } from "../theory";

/** 한 줄 근거 문장. src 는 덱 챕터(1~5) 또는 사례 문서. 슬라이드 제목·위키 편·원문 조각은 두지 않는다. */
export type Why = { text: string; src: TheoryChapter | "case" };

export type FieldOption = { value: string | number | boolean; label: string; desc?: string; why?: Why };

export type FieldMeta = {
  // …기존 필드…
  /** 입력란 자체가 왜 있는지(목적). help 는 '무엇을 입력하나', why 는 '왜 묻나'. */
  why?: Why;
  /** boolean 도 options 를 받을 수 있게 한다: [{ value: true, label: "예", why }, { value: false, label: "아니요", why }] */
  options?: FieldOption[];
};

export type DecisionOption = { id: string; label: string; desc: string; why?: Why };
export type DecisionDef = {
  // …기존 필드…
  /** '결정한 근거' 글칸의 목적 */
  rationaleWhy?: Why;
};

export type PhaseIntro = {
  /** 다리 문장 2~3줄 */
  lines: Why[];
  /** 개념 라벨로 보여 줄 개념(선택). revealOnly 개념이면 챕터만 보여 준다. */
  theory?: TheoryKey[];
};
export type PhaseDef = {
  key: string; step: StepKey; title: string; kind: PhaseKind;
  intro?: PhaseIntro;
  /** 실행 버튼별 한 줄: run 은 aa·main, readout 은 main("결과 보기") */
  actionWhy?: Partial<Record<"aa" | "main", Why>>;
};

// ClientCase(= CasePlugin 의 클라이언트 부분)에 추가: Phase 가 없는 s7·s8 의 다리 문장
stepIntro?: Partial<Record<"s7_lab" | "s8_share", PhaseIntro>>;
```

## 6. 테스트 계획

새 파일 `lib/cases/baemin/__tests__/why.test.ts`와 `lib/__tests__/theory.test.ts` 확장으로 나눠요. 원문 일치(출처 조각) 테스트는 두지 않아요(0장 3).

### 6.1 커버리지 (`why.test.ts`)

- `formMeta`의 모든 Phase(diagnose, p1~p4)의 모든 입력란이 `FIELD_WHY`(또는 `FIELD_WHY_BY_PHASE`)에 문장을 가져요.

- `WHY_NONE`은 사용자가 정한 4개(진단 보기 3, `pooled`)와 정확히 같아요.
- `decisions`의 모든 보기(P1~P4, 12개)가 `DECISION_WHY`에 있고 `RATIONALE_WHY`가 있어요.
- `phases`의 모든 Phase가 `PHASE_INTRO`에 1~3줄을 갖고, run Phase는 aa·main, readout Phase는 main의 `ACTION_WHY`를 가져요. `STEP_INTRO`에 s7·s8이 있어요.
- 반대 방향: `why.ts`의 키가 실제 입력란·보기·결정·Phase에 있어요(오타 방지).
- 길이: 한 줄은 90자 이하, 다리 문장은 Phase당 3줄 이하.

### 6.2 근거 표시 (`why.test.ts`)

- 모든 `Why.src`는 `1`~`5` 또는 `"case"`예요.
- 앱 문장에 출처 표기가 섞이지 않아요: `덱`, `위키`, `슬라이드`, `편`, `「`, `」`, `docs/`, `§`를 담지 않아요.
- `"case"` 문장은 사례 사실(정의·비중·기준값·협의 값·기능 정의)만 말하는지 리뷰에서 확인해요(자동 검사는 6.3의 숨긴 효과 숫자 검사로 대신해요).

### 6.3 스포일러 (`why.test.ts`)

검사 대상: `FIELD_WHY`, `OPTION_WHY`, `METRIC_WHY`, `DECISION_WHY`, `RATIONALE_WHY`, `ACTION_WHY`, `PHASE_INTRO`의 모든 **새** 문장. `STEP_INTRO.s7_lab`과 TrapLab 문장은 면제예요.

- 숨긴 효과 값이 들어 있지 않아요: 사례 문서 §2·§3-2의 숫자 목록(`0.55`, `0.30`, `24%`, `4.1%`, `18%`, `6.1%`, `−0.025`, `-0.025`, `0.036` 등)을 테스트 상수로 두고 검사해요. (`0.18`·`18%`처럼 §1 기준값과 겹치는 숫자는 §1 값 표기 "약 18%"를 허용 목록으로 둬요.)
- `THEORY`에서 `revealOnly`인 개념 이름이 들어 있지 않아요. 단 그 입력란의 label에 이미 같은 이름이 있으면 허용해요(예: `correction` label "다중검정 보정").
- 함정 이름이 들어 있지 않아요: `SRM`, `Sample Ratio`, `표본 비율`, `심슨`, `Simpson`, `생존`, `Survivorship`, `선택 편향`, `Selection Bias`, `신규성`, `신기효과`, `Novelty`, `Primacy`, `초두`, `이월`, `Peeking`, `피킹`, `위양성`, `ITT`, `트리거 분석`.
- 정오 힌트가 들어 있지 않아요: `정답`, `오답`, `틀린`, `틀려`, `잘못`, `올바른`, `옳은`, `권장`, `피하세요`, `하면 안`, `좋은 선택`, `나쁜 선택`.
- `PHASE_INTRO`의 `theory`에 revealOnly 개념과 함정 개념(`interference`, `interference_fix`, `peeking`, `srm`, `simpson`)이 없어요.
- **기존 맥락 문구 허용 목록:** 같은 검사를 `formMeta`의 기존 label·help·desc에도 돌리되, 아래 네 문구는 명시적으로 허용해요(0장 4). 새 문구가 이 목록에 슬쩍 추가되지 않게 목록은 스냅샷으로 고정해요.
  - `scope.os` = all desc "iOS 구버전 사용자가 포함돼요."
  - `coupon_ops` = low desc "문구 노출 조건을 채우는 사용자가 적어요."
  - `coupon_ops` = high desc "노출 대상이 늘지만 쿠폰 비용이 들어요."
  - `rationale` help "다른 설명(교란)이 가능한지 적어보세요."
