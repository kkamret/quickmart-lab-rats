# 배민 실습: 모든 선택지에 "왜 이 선택지?" 한 줄 달기 (설계)

- 작성일: 2026-10-09
- 범위: 배민 사례(`lib/cases/baemin`)의 진단 → P1 설계·실행·결과·결정 → P2 → P3 → P4 → s7 함정 연구소 → s8 직소 공유. 앱 코드는 이 문서에서 바꾸지 않아요.
- 브랜치: `feat/baemin-choice-rationale` (`feat/baemin-theory-logic` 위). PR #20과 별도 PR로 내요.
- 함께 읽을 문서: `docs/cases/baemin.md`(진실의 원천), `docs/superpowers/specs/2026-10-09-baemin-theory-logic-design.md`(판정 로직), `docs/theory-coverage.md`(패러프레이즈 은행), `lib/theory.ts`(THEORY, FIELD_THEORY, STEP_THEORY).
- 인용 규칙: 덱은 슬라이드 번호 대신 **제목**(「…」)으로, 위키는 **편·절**로 인용해요. 덱 제목은 `docs/lecture/build/build.js`의 `content(…, …, "제목")` 세 번째 인자와 같아요.

## 1. 목표·비목표·원칙

### 1.1 목표

- 배민 실습 흐름에서 학생에게 보이는 **모든 선택**(select·multiselect·boolean 보기, number·text 입력란의 목적, 결정 보기, 진단 보기, 실행 버튼)에 "왜 이 선택지가 있는지"를 한 줄로 보여 줘요. 학생이 설계·선택·실행하면서 이론을 떠올리게 하는 게 목적이에요.
- Phase(진단, P1 설계, P1 실행, P1 결과·결정, P2, P3, P4, s7, s8)마다 "왜 여기 왔고, 앞 결과가 무엇으로 이어지는지"를 2~3줄 다리 문장으로 보여 줘서, 모든 선택이 하나의 큰 흐름 안에서 이어지게 해요.
- 모든 문장은 **덱·위키 문장의 가까운 패러프레이즈**이고, 출처 조각을 문장마다 기록해 추적할 수 있게 해요. 사례 자체의 사실(예: 안드로이드가 일 유입의 약 59%)은 `docs/cases/baemin.md` §1에서만 가져와요.

### 1.2 비목표

- 정답·오답을 알려 주지 않아요. 맞다/틀리다는 지금처럼 정답 공개(판정 근거 `judge` reason, 플래그 `why`)에서만 보여요.
- 시뮬레이터, 판정 로직, 루브릭은 바꾸지 않아요.
- 토스·당근·넷플릭스는 이번 범위가 아니에요. 다만 UI 변경은 공통 컴포넌트에 들어가므로, 데이터(`why`)가 없는 사례는 지금과 똑같이 보이게 해요.
- 덱·위키를 고치지 않아요. 근거가 없는 줄은 GAP으로 남기고 사용자가 결정해요(5장).

### 1.3 원칙

1. **출처만 쓴다.** 앱에 보이는 이론 문장은 덱 또는 위키 문장 하나 이상의 가까운 패러프레이즈예요. 우리가 지어낸 설명은 넣지 않아요. 근거가 없으면 GAP으로 표시하고 앱에 넣지 않아요.
2. **사례 사실은 §1에서.** 유입·세그먼트 비중·대조군 기준값은 사례 문서 §1(고정 모집단)에서만 가져와요. §2(숨긴 효과), §3-2(반영 규칙), §3-3(플래그)의 숫자와 규칙은 쓰지 않아요. 기능 정의(P3 노출 조건, P4의 B·C 정의)처럼 §0 원문 사실의 **설계 부분**을 쓰는 줄은 표에 `사례 §0(설계)`로 따로 표시하고 사용자 확인을 받아요(5장 G-6).
3. **스포일러 금지.** 정답 공개 전 문장은 함정 이름(SRM, 심슨, 생존 편향, 신규성 효과, Peeking 등), 플래그 이름·라벨(`FLAG_LABELS`), "틀렸다/맞다" 힌트를 담지 않아요. "이 보기가 왜 있는지, 어떤 상황에서 쓰는지"만 중립적으로 말해요. 예: `peek_stop`이 위양성을 늘린다고 말하지 않고, 세션·페이지뷰가 틀렸다고 말하지 않아요. 덱 문장에 함정 결과(예: "이월 효과로 차이가 작게 측정된다")가 같이 있으면 그 부분은 빼고 "언제 쓰나" 부분만 가져와요.
4. **한 선택지에 한 줄.** 보기마다 한 줄(길어도 두 문장)이에요. 입력란 자체의 목적은 입력란 줄 한 개로 말해요.
5. **앱 안에서는 챕터 라벨만.** 앱 문장에 슬라이드 제목·번호·위키 편·링크를 쓰지 않아요. 이론 연결은 기존처럼 `theoryLabel`(정답 공개 전 함정 개념이면 `theoryChapterOnly`)로만 보여요. 출처 조각은 테스트 전용 파일에만 둬요(4.3).
6. **기존 테스트를 지킨다.** `lib/__tests__/theory.test.ts`의 "THEORY note 문장을 폼 문구에 그대로 넣지 않는다", "revealOnly 개념은 s7 밖 스텝 이론 줄에 넣지 않는다"를 새 문구에도 똑같이 적용해요(6장).
7. **앱 동작 안내는 이론 주장과 구분한다.** "제출한 설계대로 돌아가요"처럼 앱이 어떻게 움직이는지 말하는 문장은 이론 주장이 아니므로 출처 태그를 `app`으로 달아요. 이런 문장도 스포일러 규칙은 똑같이 지켜요.

## 2. 흐름 지도

### 2.1 큰 흐름

덱 「A/B 테스트는 일곱 단계로 돌아간다」의 7단계(목표와 지표 → 가설 → 대조군·실험군 → 무작위 배정 → 실행과 데이터 수집 → 분석과 비교 → 결정과 반복)를 배민 네 번의 실험에 겹치면 아래처럼 이어져요.

```text
s1 진단(관찰 데이터, 문제 좁히기)
  └─ s2 P1 설계(가설 → 범위 → 단위 → 지표 → α·검정력 → 기간·투입 → 램프업·분석·중간 확인·집계)
       └─ s3 P1 실행(A/A로 시스템 점검 → 본 실험)
            └─ s4 P1 결과 읽기 → 결정(배포·접기·재실험)
                 └─ s5 P2 확대(내적 → 외적 타당성) → 결과 → 결정(배포 + 다음 가설)
                      └─ s5 P3 혜택 넛지(Secondary·Driver에서 다음 가설) → 결과 → 결정
                           └─ s6 P4 부족 금액 추천(A/B/n) → 결과 → 결정
                                └─ s7 함정 연구소(앞에서 스친 함정을 이름과 함께)
                                     └─ s8 직소 공유(효과 크기 × 비용 × 리스크로 말하기, 배운 점 남기기)
```

## 6. 테스트 계획

새 파일 `lib/cases/baemin/__tests__/why.test.ts`와 `lib/__tests__/theory.test.ts` 확장으로 나눠요.

### 6.1 커버리지 (`why.test.ts`)

- `formMeta`의 모든 Phase(diagnose, p1~p4)의 모든 입력란이 `FIELD_WHY`(또는 `FIELD_WHY_BY_PHASE`)에 문장이 있거나 `WHY_EXEMPT`에 있어요.
- select·multiselect 입력란의 모든 보기가 `OPTION_WHY`(지표 3칸은 `METRIC_WHY`)에 있거나 `WHY_EXEMPT`에 있어요. boolean 입력란은 true·false 문장이 모두 있어요.
- `decisions`의 모든 보기(P1~P4, 12개)가 `DECISION_WHY`에 있고, `RATIONALE_WHY`가 비어 있지 않아요.
- `phases`의 모든 Phase가 `PHASE_INTRO`에 1~3줄을 갖고, run Phase는 aa·main, readout Phase는 main의 `ACTION_WHY`를 가져요. `STEP_INTRO`에 s7·s8이 있어요.
- 반대 방향: `why.ts`의 키가 실제 입력란·보기·결정·Phase에 있어요(오타 방지, 기존 FIELD_THEORY 테스트와 같은 방식).
- `WHY_EXEMPT`는 사용자가 승인한 목록과 정확히 같아요(스냅샷). GAP을 해결하면 이 목록에서 빼고 문장을 넣어요.
- 길이: 한 줄은 90자 이하, 다리 문장은 Phase당 3줄 이하.

### 6.2 스포일러 (`why.test.ts`)

검사 대상: `FIELD_WHY`, `OPTION_WHY`, `METRIC_WHY`, `DECISION_WHY`, `RATIONALE_WHY`, `ACTION_WHY`, `PHASE_INTRO`의 모든 문장. s7 다리 문장(`STEP_INTRO.s7_lab`)과 TrapLab 문장은 면제예요.

- 플래그 코드(`ALL_FLAGS`)와 라벨(`FLAG_LABELS`의 값)이 들어 있지 않아요.
- 함정 낱말 목록이 들어 있지 않아요: `SRM`, `Sample Ratio`, `표본 비율`, `심슨`, `Simpson`, `생존`, `Survivorship`, `선택 편향`, `Selection Bias`, `신규성`, `신기효과`, `Novelty`, `Primacy`, `초두`, `이월`, `Peeking`, `피킹`, `희석`, `과소평가`, `과대평가`, `오염`, `위양성`, `ITT`, `트리거 분석`.
- 정오 힌트 낱말이 들어 있지 않아요: `정답`, `오답`, `틀린`, `틀려`, `잘못`, `올바른`, `옳은`, `권장`, `피하세요`, `하면 안`, `좋은 선택`, `나쁜 선택`.
- `THEORY`에서 `revealOnly`인 개념 이름이 들어 있지 않아요. 단 그 입력란의 label에 이미 같은 이름이 있으면 허용해요(예: `correction` label "다중검정 보정", `trigger_logging` label "트리거 조건 로깅").
- 숨긴 효과 값이 들어 있지 않아요: 사례 문서 §2·§3-2의 숫자 목록(`0.55`, `0.30`, `24%`, `4.1%`, `18%`, `6.1%`, `−0.025`, `-0.025`, `0.036` 등)을 테스트 상수로 두고 검사해요.
- `PHASE_INTRO`의 `theory`에 `revealOnly` 개념과 함정 개념(`interference`, `interference_fix`, `peeking`, `srm`, `simpson`)이 없어요(기존 STEP_THEORY 테스트와 같은 규칙).

### 6.3 출처 (`why.test.ts`)

- 앱에 보이는 모든 문장 키가 `WHY_SOURCES`에 1개 이상의 출처를 가져요. `app`만 있는 문장은 허용 목록(앱 동작 안내)에 있어야 해요.
